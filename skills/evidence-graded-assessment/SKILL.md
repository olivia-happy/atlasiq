# 多因素评估的证据分级方法

> **核心理念**：评估表最大的问题不是算得不准，而是**算不出/算不准的地方被一个数字盖住了**。
> 一个「政策确定性 64 分」看起来是结论，实际上可能只是基线——看的人不知道它是测出来的还是拍的。
> 这套方法只做一件事：**把"我们不知道"变成一等的、可见的输出。**

---

## 强制工作流

### Phase 0：判断是否需要完整流程

- 只是给一个已知公式的指标算个数 → **跳过本 Skill**
- 要做一个多因素评估表 / 决策矩阵 → **走完整流程**

### Phase 1：固定因素集（不要临场想因素）

因素集必须**在评估开始前定死并版本化**，否则不同项目之间不可比，也无法解释"这一版为什么分变了"。

| 要求 | 说明 |
| --- | --- |
| 因素个数 | 6–9 个。少于 6 个会漏，多于 9 个人读不动 |
| 每个因素 | 一个 `key`（机器用）+ 一个 `label`（人读）+ 一句 `explanation`（说清它衡量什么） |
| 权重 | 显式写出，且必须能被质疑和调整。**不要用模型生成的"重要性排序"** |
| 版本 | 因素集一改就是新版本。旧版本的快照必须能读出来 |

**输出**：一张因素定义表，格式如下（示例取自海外光伏市场准入）：

```
market_growth      市场增长        权重 0.35
power_demand       电力需求        权重 0.20
solar_resource     光照与发电潜力   权重 0.20
policy_auction     政策与招标      权重 0.25
macro_finance      宏观与融资      权重 0.15
supply_trade       供应链与贸易    权重 0.10
```

### Phase 2：三态披露（本方法论的核心）

每个因素**不许直接给分**，必须先判定它处在哪一态：

| 状态 | 判定条件 | 分值怎么来 | 页面怎么显示 |
| --- | --- | --- | --- |
| `observed` | 有结构化观测数据，且能回溯到来源 ID | 基线 + 有区间上限的修正量 | 显示分值、来源、覆盖率、"本次刷新" |
| `assumption` | 只有文本证据，尚未人工确认 | **回落基线，不做修正** | 显示基线分 + "存在文本证据但未确认" |
| `insufficient` | 既无观测也无已确认证据 | **回落基线** | 显示基线分 + "当前无充分观测，显示基线而非实时测量" |

**三条硬规则**：

1. **修正量必须有上限**。例：光照因素按 `(pv_yield - 1400) / 50` 计算，但 `clamp(-8, +8)`；
   宏观因素按 `(gdp_growth - 2)` 计算，`clamp(-6, +6)`。没有上限的修正 = 一个异常值污染全表。
2. **回落基线时必须明说**。`assumption` 和 `insufficient` 都给基线分，但解释文案必须不同——
   前者是"有证据没确认"，后者是"什么都没有"。这两种情况在决策上完全不同。
3. **覆盖率必须一起输出**。每个因素带 `coverage_ratio`（有几个指标真的拿到了）和 `missing_ratio`。
   例：某因素定义了 2 个指标、只拿到 1 个 → `coverage_ratio = 0.5`，解释里写"基于 X 的 1/2 个可用观测计算；未提供的指标保持缺失"。

### Phase 3：证据挂载

- 每条结论必须能回到**来源 ID + 证据 ID**，页面与导出的报告**共用同一份快照**（否则两处口径会漂移）
- 信源要独立于因素记录健康度：`live` / `degraded` + `last_success_at`
- **降级不静默**：信源失败时置 `degraded` 并保留上次成功时间与标签，而不是清空或假装成功

### Phase 4：AI 边界的划分（评估类产品必答）

| 环节 | 谁负责 | 为什么 |
| --- | --- | --- |
| 因素评分 / 情景 / 敏感性 | **确定性规则** | 可复现。模型不许改分 |
| 研究简报 / 结论文本 | 受控 AI（可选） | 只据服务端证据组织表达 |
| 是否推进 / 是否准入 | **人** | 系统永不自动准入、淘汰或改状态 |
| 信号提醒 | 系统仅提醒复核 | 已确认证据触发复盘，不自动改写结论 |

**降级要求**：AI 不可用时绝不静默；降级回答仍须带可引用证据，且所有运行写审计。

### Phase 5：输出必须包含的边界声明

一份合格的评估产物，末尾必须写清：

- 数据源边界（哪些是公开数据、有无付费源、有无爬虫规避）
- **哪些因素是回落基线而非实测**（点名，不要只说"仅供参考"）
- 演示/样例结果不代表真实结论、不构成投资建议
- 下一步要补的指标清单（以及补上它们需要什么授权）

## 反模式（绝对要避免）

| # | 反模式 | 正确做法 |
| --- | --- | --- |
| 1 | 因素临场想，每个项目都不一样 | 因素集版本化，改即新版本 |
| 2 | 用模型排序决定权重 | 权重显式写出，可被人质疑 |
| 3 | 所有因素都给一个"精确"分值 | 先判三态，回落基线的要标注 |
| 4 | 修正量无上限 | 每个修正量 clamp 到区间 |
| 5 | 只输出分值，不输出覆盖率 | 分值 + 覆盖率 + 缺失率一起出 |
| 6 | 页面和报告各算一遍 | 共用同一份 snapshot |
| 7 | 信源失败就清空数据 | 置 degraded + 保留上次成功时间 |
| 8 | 让模型决定要不要推进 | 决策永远由人拍板 |
| 9 | 边界声明写成一句"仅供参考" | 点名哪些因素回落了基线 |

## 快速启动模板

当用户说"帮我评估一下 XXX 值不值得做/进"时：

```
在做评估表之前，先把三件事定下来：

1. 因素集：你希望从哪 6–9 个维度看？（我按你的行业给一版，你改）
2. 权重：哪个维度对你最重要？权重写死，后面不改。
3. 数据可得性：这 6–9 个维度里，你现在真的能拿到数据的有几个？
   —— 剩下的我会标成"回落基线"，不会假装它们被测量过。

另外提前说清楚：这份表里我会显式标出哪些格子是"我们不知道"。
如果你希望所有格子都有漂亮数字，这套方法可能不适合你。
```

## 与 AI 产品岗的对应关系

这套方法直接对应三类岗位要求：

- **AI 边界设计**：谁能改分、谁能下结论、AI 挂了怎么办——Phase 4 就是答案
- **评测与可信度**：覆盖率、缺失率、三态披露，是可被追问的量化口径，不是"我们很严谨"这种形容词
- **数据治理**：来源 ID、证据 ID、快照共用、信源健康度，是工程层能落地的东西

被追问"你怎么保证结论可信"时，答：**"我没有保证它可信，我做的是让不可信的部分显式可见——哪些因素是实测的、哪些是基线的，都写在解释里。"**
